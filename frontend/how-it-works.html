How It Works

A plain-English explanation of the TCP socket programming concepts used in this project — written for an ECE college student.

1. What is TCP?

TCP (Transmission Control Protocol) is one of the main protocols of the Internet. It provides a reliable, ordered, error-checked channel between two computers.

  • Reliable – if a packet is lost, TCP automatically retransmits it.
  • Ordered – data arrives in the same order it was sent.
  • Connection-oriented – a connection must be established before data can flow (the famous three-way handshake: SYN → SYN-ACK → ACK).

Because TCP guarantees delivery and order, it is ideal for file transfer. If even one byte of a file is lost, the received file would be corrupted — TCP prevents this.

2. What is Socket Programming?

A socket is a software endpoint that programs use to send and receive data over a network. Think of a socket as the plug-and-socket pair at each end of a telephone cable.

In Python we use the built-in socket library:

  • socket.socket(AF_INET, SOCK_STREAM) — creates a TCP socket.
  • sock.connect((ip, port)) — sender connects to the receiver.
  • sock.bind((host, port)) + sock.listen() — receiver listens for connections.
  • sock.sendall(data) — sends bytes reliably.
  • sock.recv(n) — reads up to n bytes (may return fewer — see chunk reading below).

3. Why Use TCP for File Transfer?

Alternative protocols like UDP are faster but do not guarantee delivery. A single lost UDP packet would produce a corrupted file with no automatic recovery.

TCP's built-in reliability means we can focus on the application logic (metadata, acknowledgements, checksum verification) instead of writing our own retransmission logic.

4. File Transfer Communication Flow

This is the exact sequence implemented in tcp_sender.py and tcp_receiver.py:

TCP Connect → File Metadata → Receiver ACK → File Chunks → File Reconstruction → Final ACK → Transfer Complete
  1. TCP Connection — The sender calls sock.connect(receiver_ip, receiver_port). The OS performs the three-way handshake automatically.
  2. File Metadata — The sender transmits a small JSON message containing the filename, file size, and SHA-256 checksum. This is sent as a framed message (see §6).
  3. Receiver ACK — The receiver validates the filename (no path traversal, no illegal characters) and checks for duplicate filenames. If everything is fine, it sends back ACK; otherwise it sends REJECT.
  4. File Chunks — The sender reads the file in 4096-byte blocks and calls sock.sendall(chunk) for each block.
  5. File Reconstruction — The receiver appends each chunk to a new file on disk, counting the bytes received.
  6. Verification — When all bytes are received, the receiver checks (a) the total byte count matches the declared file size, and (b) the SHA-256 checksum matches the one sent in the metadata.
  7. Final ACK — The receiver sends SUCCESS or FAILURE. The sender displays the result to the user.

5. Message Framing — Why It Matters

TCP is a stream protocol. When you send 100 bytes, the receiver's recv() call might return 40 bytes the first time and 60 bytes the next — or all 100 at once. There is no concept of message boundaries in TCP by default.

To fix this, we use length-prefixed framing (implemented in protocol.py):

  • Before every control message (metadata, ACK, SUCCESS…) we prepend a 4-byte big-endian integer that holds the message length.
  • The receiver first reads exactly 4 bytes to learn the length, then reads exactly that many bytes.
  • File data chunks are handled differently: we know the total file size from the metadata, so we keep reading min(CHUNK_SIZE, remaining) bytes until all bytes arrive.

The helper function recv_exact(sock, n) in protocol.py loops on sock.recv() until exactly n bytes have been accumulated — correctly handling partial reads.

6. SHA-256 Checksum — File Integrity Verification

A checksum is a short fixed-length value derived from a file. If even one bit of the file changes, the checksum changes completely.

We use SHA-256 (from Python's hashlib library):

  • The sender computes the SHA-256 hash of the file before sending and includes it in the metadata.
  • The receiver computes the SHA-256 hash of the data as it arrives, byte by byte.
  • After all chunks are written, the two hashes are compared. A mismatch means the file was corrupted in transit — the receiver deletes the file and sends FAILURE.

7. System Architecture

This project has a three-layer architecture:

  • Browser (HTML + JS) — the user interface. Sends files to the backend using HTTP multipart upload and polls the backend for receiver events.
  • FastAPI backend (main.py) — acts as a bridge. It accepts the browser's HTTP requests and calls the TCP sender/receiver code.
  • TCP layer (tcp_sender.py, tcp_receiver.py, protocol.py) — does the actual network file transfer between two computers using raw TCP sockets.

The reason we need a backend is that browsers cannot open raw TCP sockets for security reasons. The FastAPI server runs on the same machine and acts as the TCP client/server on behalf of the browser.

8. File Safety and Security

  • Filename validation — The receiver rejects filenames containing path separators (/, \, ..) or unusual characters to prevent path traversal attacks.
  • No overwriting — If a file named report.pdf already exists, the receiver saves the new file as report_1.pdf, then report_2.pdf, and so on.
  • Incomplete file cleanup — If the connection drops mid-transfer, the incomplete file is deleted automatically.

9. Viva Questions & Answers

Q1. What is the difference between TCP and UDP?
TCP is connection-oriented and guarantees reliable, ordered delivery. UDP is connectionless and faster but offers no delivery guarantee. We use TCP for file transfer because we cannot afford to lose any bytes of the file.
Q2. What is a socket?
A socket is a software interface that allows a program to send and receive data over a network. It is identified by an IP address and a port number. In Python, the socket.socket() call creates one.
Q3. What is the three-way handshake?
It is how TCP establishes a connection. The client sends SYN, the server replies with SYN-ACK, and the client sends ACK. After this, data can flow in both directions.
Q4. Why do we read the file in chunks instead of all at once?
Large files may not fit in RAM. Reading in 4096-byte chunks keeps memory usage constant regardless of file size. TCP can also only handle limited amounts of data in a single send, so chunking aligns with how the protocol naturally works.
Q5. Why can one recv() call return fewer bytes than requested?
TCP is a stream protocol. The OS may split data across multiple TCP segments. A recv() call returns whatever bytes are currently in the OS buffer, which may be less than the requested amount. Our recv_exact() function loops until the full amount arrives.
Q6. What is message framing and why do we need it?
Since TCP has no message boundaries, we prepend each control message with a 4-byte length header. The receiver reads the length first, then reads exactly that many bytes. This is called length-prefix framing.
Q7. What is a SHA-256 checksum and why do we use it?
SHA-256 is a hash function that produces a 64-character hexadecimal string from any input. Even a single bit change in the file produces a completely different hash. We compare the sender's hash with the receiver's computed hash to verify that the file arrived uncorrupted.
Q8. What is an ACK?
ACK stands for Acknowledgement. In our protocol, after receiving the metadata the receiver sends back a simple "ACK" byte string to tell the sender it is ready to receive the file. If the metadata is invalid, it sends "REJECT" instead.
Q9. What happens if the connection drops midway through a transfer?
The recv_exact() function raises a ConnectionError because it tries to read bytes that never arrive. The receiver catches this, deletes the incomplete file, and reports a failure. The sender also catches the exception and displays an error to the user.
Q10. What is a port number?
A port number (0–65535) identifies a specific application or service on a computer. The IP address gets the data to the right machine; the port gets it to the right application. In this project, both sides agree to use port 9001 by default.
Q11. Why does the browser upload the file to its own backend before TCP transfer?
Web browsers cannot open raw TCP sockets (for security reasons). So the browser uploads the file to its local FastAPI server using HTTP. The FastAPI server then opens the real TCP connection and transmits the file to the remote receiver.
Q12. How does the receiver prevent overwriting existing files?
Before saving, the receiver checks whether a file with the same name already exists in the destination folder. If it does, it appends _1, _2, etc., to the filename until it finds a name that does not exist.
